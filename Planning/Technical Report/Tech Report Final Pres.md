How things function together (runtime flow)

API request arrives at simulation.py (FastAPI).

Endpoints call into core services:

- `db_manager` (`DatabaseManager`) for
  persistence (drivers, teams, tracks, championships).
- `race_simulator` (`RaceSimulator`) — the
  Monte Carlo engine that should coordinate discipline-specific engines.

`RaceSimulator` (in `disciplines/race_simulation.py`) is expected to:

- Build a `SimulationContext` (drivers,
  teams, track, weather, rules).
- Dispatch to a discipline engine (e.g.,
  `single_seater/single_seater_engine.py`) which implements the discipline's
  logic: lap times, reliability, pit strategy, weather effects.
- Use discipline `rulebook` (e.g.,
  `SingleSeaterRulebook`) to validate vehicles before sim.
- Return ordered `RaceResult` objects;
  results are optionally stored via `DatabaseManager`.

`DatabaseManager`:

- Initializes schema (using `SCHEMA_SQL` in
  models.py), provides CRUD and query methods (drivers, teams, staff, tracks,
  championships, race_results).

`systems/*` provide cross-cutting responsibilities:

- `championship_manager` applies points
  systems and carries championship standing updates.
- `currency_system` fetches/exposes exchange
  rates (caching, using currency_cache.json).
- `intelligent_name_generator` creates
  driver names (uses NameAPI or local fallback).

`vehicles` components are composed to represent a `RaceCar` object and
validated via rulebooks per discipline.

This
is a classic layered design:

- API
  layer (simulation.py) -> orchestration layer (`RaceSimulator`, `systems/*`)
  -> discipline engines & rulebooks -> domain models & persistence
  (`database/*`) -> assets and components (`vehicles/*`, `ai/*`, `data/*`).

# [Executive Summary]()

The project delivers a multi-discipline
motorsport management simulator designed to provide statistically rich,
credible racing behaviour and deep team-management systems within a
lightweight, locally runnable environment. The report documents the motivation,
aims, architecture, implementation and requirements of the system, establishing
a formal basis for the completed work and future development.

The simulator addresses the limited
scope of existing titles by integrating multiple racing disciplines, detailed
management mechanics and a realtime event-driven race engine. Background
influences include modding work on car-centric games and exposure to simple
retro racers, guiding the emphasis on expressive vehicle systems and low-fi
visual presentation.

Core aims include broad discipline
coverage, depth of management features (contracts, staff, budgets, setup), and
practical deployability. Planned features comprise per-frame racing telemetry,
discipline modules, a compact driver/team model, a PyQt6 interface, staff and
budget systems, and playtesting tools for collecting quantitative metrics such
as DNFs, lap-time distributions and volatility.

The technology stack is based on Python
3.13, FastAPI, Uvicorn, Pydantic, SQLite, NumPy/pandas/SciPy, PyTorch, PyQt6,
and geometry libraries (Shapely, bezier). This combination supports rapid
iteration, scientific analysis, portable distribution and performant desktop
visualisation.

Functional requirements are prioritised
into core gameplay tasks (reading driver data, reading race configuration,
generating race results), extended career-mode functionality (championship
logic, team management, driver/staff contracts, budgets, ageing and skill
updates), and optional enhancement features (custom tracks, branding, appearance
updates, and creation of new driver/staff pools). The report also outlines the
system structure: requirements and use cases, architecture, and GUI design.

# 1

Introduction

## []()[1.1       Background]()

Motorsport
management simulation games have been a niche but dedicated gaming genre since
the 1990s. However, most existing games focus on a single discipline (usually
Formula 1) or lack the depth required for authentic simulation. Games like
Football Manager have shown that deep statistical simulation can create
compelling gameplay, but motorsport has remained underserved. The motivation
stemmed from both personal interest in motorsport and the technical challenge
of building a complex simulation system that balances realism with performance.

Over the
summer I spent time modding and studying car-centric games being Juiced and
Need for Madness. That work reinforced my interest in vehicle dynamics and UI
for car-focused tools, and it influenced the direction of this project:
continue with car-centric coding, reuse practical techniques from the modding
workflows and prioritise features that make vehicle and team systems expressive
for players.

During
an internship at HSE, my manager would bring out a Raspberry Pi and we would
play simple racing games from his childhood like Micro Machines during lunch,
those sessions inspired parts of the game's low‑fi graphics
and vehicle‑focused
presentation.

## [1.2       Aims]()

High
level aims

* Broader coverage:
  provide a single platform that supports multiple racing disciplines so
  gameplay and balance can be compared across formats.
* Depth over novelty:
  prioritise detailed management systems (contracts, staff effects, budget
  scaling, vehicle setup) and credible on-track behaviour.
* Practical
  deliverability: keep the project runnable on a standard computer using a
  single repository and lightweight dependencies.

Planned
features

* Realtime
  decision-driven racing engine that emits per-frame position updates and
  discrete events (DNF, lap complete).
* Discipline modules
  enabling per-discipline configuration for rules, scoring and vehicle
  characteristics.
* Compact driver/team
  data model with core attributes and career metadata.
* PyQt6 GUI for
  visualisation.
* Team and staff systems
  (budgets, operations rating, strategy profiles) that influence performance
  over a season and beyond.
* Playtesting and tuning
  tools: scripts that run short scenarios and collect metrics (DNFs,
  position volatility, lap times). For assistance of tuning data for the
  final product.

  Pydantic:
* Reason: Fast,
  async-first web framework with automatic validation and OpenAPI
  generation, Uvicorn is a lightweight ASGI server. Pydantic gives robust
  model validation for API schemas.
* Advantage over
  alternatives: Faster development and clearer request/response models vs.
  Flask, simpler async support than Django, better runtime performance and
  type-safety compared with many microframeworks.
* SQLite:
* Reason: Single-file,
  zero-admin persistent storage that’s simple to bundle with the project
  and ideal for a desktop game/simulator.
* Advantage over
  alternatives: Far easier to set up than PostgreSQL or MySQL for local dev
  and distribution, good performance for moderate-sized datasets used by
  the game.
* NumPy, pandas, SciPy:
* Reason: Battle-tested
  numerical and data-manipulation libraries for vectorised computations,
  statistics, and analysis/export tasks.
* Advantage over
  alternatives: Rich ecosystem, performance (NumPy vectorisation), and
  interoperability, pandas simplifies CSV/analysis tasks used in simulation
  telemetry.
* PyTorch (torch):
* Reason: Provides
  experimental ML capability for things like driver behaviour models,
  reinforcement learning, or pattern extraction.
* Advantage over
  alternatives: Large community, flexible dynamic graphs, Pythonic API.
* PyQt6:
* Reason: Stable,
  native-feeling desktop GUI toolkit with good performance for interactive
  visualisers and complex widgets.
* Advantage over
  alternatives: Better native widget fidelity and performance than Tkinter,
  simpler native look and more features than Kivy for desktop apps, lighter
  and more responsive than Electron-based stacks.
* Pydantic, Faker,
  python-dotenv, requests:
* Reason:
* Pydantic: schema
  validation for APIs and config.
* Faker: realistic
  seeded name generation for drivers/teams.
* python-dotenv: simple
  environment config loading for dev/prod differences.
* requests: reliable
  HTTP client for exchange rates, optional external APIs.
* Advantage over
  alternatives: Each is lightweight, well-documented and widely used in
  Python projects, making onboarding easier.
* Shapely, bezier:
* Reason: Provide robust
  geometry primitives and smooth curve utilities for track geometry,
  collision checks and spline-based track rendering.
* Advantage over
  alternatives: Higher-level geometry operations than rolling your own,
  bezier is specialised for curve maths which simplifies track
  interpolation.
* Why this stack overall:
* Focused on rapid
  development, reproducible local runs, and a strong scientific toolchain
  for simulation and post‑hoc analysis. It keeps
  runtime simple for desktop distribution (SQLite, PyQt6) while allowing
  sophisticated backend services and experimentation (FastAPI, NumPy,
  PyTorch). The choices balance developer productivity, portability, and
  the ability to scale particular subsystems later if needed (e.g., swap
  SQLite → PostgreSQL, offload heavy simulation to compiled modules or
  worker services).

## 2.31  Data

Requirements

This section documents the project's
persistent database schema and related data requirements. The database uses a
lightweight SQLite schema (SCHEMA_SQL) with seven primary tables and a small
set of indexes.

### 2.31.1

Database Schema

The database contains the following
tables (principal columns shown):

#### 2.31.1.1

Drivers

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Biographical: name (TEXT NOT NULL),
  nationality (TEXT NOT NULL), birth_date (TEXT NOT NULL)
* Performance attributes (REAL,
  0.0–100.0 with CHECK where applicable): speed, racecraft, consistency,
  fitness, reactions, pressure, setup_knowledge, fuel_management,
  tyre_management, feedback, adaptability
* Career statistics: career_points
  (INTEGER), career_podiums (INTEGER), career_starts (INTEGER), career_dnf
  (INTEGER), seasons_active (INTEGER)
* Discipline wins:
  single_seater_wins, touring_wins, rally_wins, street_wins, drag_wins,
  rallycross_wins, endurance_wins (INTEGER)
* Career progression & metadata:
  peak_performance_age (INTEGER), retirement_age (INTEGER), learning_rate
  (REAL), form_trend (REAL), biography (TEXT), career_highlights (TEXT),
  preferred_discipline (TEXT), career_phase (TEXT)
* Team/contract: current_team_id
  (INTEGER), previous_teams (TEXT JSON-string), contract_length (INTEGER),
  salary (REAL), name_locale (TEXT)
* Foreign key: current_team_id
  references teams(id)

#### 2.31.1.2

Teams

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Fields: name (TEXT NOT NULL
  UNIQUE), nationality (TEXT NOT NULL), discipline (TEXT NOT NULL), tier
  (TEXT NOT NULL), budget (REAL NOT NULL)
* Optional: founded_year,
  team_principal, history (TEXT), total_wins, total_podiums, championships
  (INTEGER)
* Performance attributes:
  operations_rating (REAL DEFAULT 50.0, CHECK 0.0–100.0), strategy_profile
  (TEXT)

#### 2.31.1.3

Tracks

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Fields: name (TEXT NOT NULL),
  country (TEXT NOT NULL), primary_discipline (TEXT NOT NULL)
* Physical/auxiliary:
  is_point_to_point (INTEGER 0/1), joker_enabled (INTEGER 0/1),
  instructions_json (TEXT), geometry_json (TEXT), pit_entry_index,
  pit_exit_index
* Note: additional track geometry and
  physical attributes are modelled in the Track dataclass and can be
  persisted in JSON fields when required.

#### 2.31.1.4

Championships

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Fields: name (TEXT NOT NULL
  UNIQUE), discipline (TEXT NOT NULL), season_length (INTEGER NOT NULL),
  points_system (TEXT NOT NULL), current_season (INTEGER NOT NULL)

#### 2.31.1.5

Races

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Foreign Keys: championship_id
  (REFERENCES championships(id)), track_id (REFERENCES tracks(id))
* Fields: season (INTEGER),
  round_number (INTEGER), race_date (TEXT NOT NULL), weather_conditions
  (TEXT), laps (INTEGER), status (TEXT DEFAULT 'scheduled')

#### 2.31.1.6

RaceResults

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Foreign Keys: race_id (REFERENCES
  races(id)), driver_id (REFERENCES drivers(id)), team_id (REFERENCES
  teams(id))
* Fields: position (INTEGER NOT
  NULL), fastest_lap (INTEGER 0/1 DEFAULT 0), points (INTEGER DEFAULT 0),
  dnf_reason (TEXT)
* Expanded persisted fields:
  time_seconds, grid_position, laps_completed, best_lap_time,
  average_lap_time, pitstops, tyre_strategy, penalties_seconds,
  penalty_reason, gap_to_winner_seconds, status (TEXT DEFAULT 'FINISHED'),
  recorded_at

#### 2.31.1.7

StaffMembers

* Primary Key: id (INTEGER PRIMARY
  KEY AUTOINCREMENT)
* Fields: name (TEXT NOT NULL), role
  (TEXT NOT NULL), rating (REAL DEFAULT 50.0), current_team_id (INTEGER
  REFERENCES teams(id))

### 2.31.2

Data Integrity

* Foreign key constraints:
  Implemented for drivers.current_team_id -> teams(id),
  races.championship_id -> championships(id), races.track_id ->
  tracks(id), race_results.(race_id,driver_id,team_id) ->
  races/drivers/teams, and staff_members.current_team_id -> teams(id).
* CHECK constraints: Core driver and
  team numeric attributes (e.g., speed, operations_rating) include
  CHECK(range) clauses in SCHEMA_SQL to enforce 0.0–100.0 where appropriate.
* UNIQUE constraints: teams.name and
  championships.name are declared UNIQUE to prevent duplicates.
* NOT NULL: Critical fields use NOT
  NULL (e.g., driver name, nationality, birth_date; team name, discipline,
  budget; race race_date).

### 2.31.3

Performance Optimisations

* Indexes: The schema creates the
  following indexes: idx_drivers_team on drivers(current_team_id),
  idx_teams_discipline on teams(discipline), and idx_race_results_driver on
  race_results(driver_id).
* Query patterns: Query patterns
  favour small, targeted queries and joins; larger or optional payloads are
  stored as JSON/text to avoid wide tables.
* Composite lookups are supported to
  efficiently query races by championship, season and round, and to fetch
  results by race.

## [2.35  Design

and Architecture]()

### [2.35.1     Current]()

Momentum
is built on Python 3.13 and uses PyQt6 for the GUI. The architecture consists
of specialised classes that manage different aspects of the simulation. The
core simulation uses a realtime agent-based approach where drivers are
autonomous AI entities making decisions at 30 FPS based on race conditions and
their attributes.

#### 2.35.1.1

Core Architecture Classes

The
simulation architecture can be broken down into key classes that handle
initialisation, state management, player interaction, and visual
representation.

##### 2.35.1.1.1

MomentumLauncher (Application Controller)

Location:
Momentum/Python/GUI/launcher.py

This
class manages the overall application lifecycle. It initialises the PyQt
application, manages transitions between the main menu and race windows, and
handles player configuration.

When
you start Momentum, the launcher creates a QApplication and shows the
MainMenuWindow. When the player selects a driver and starts a race it creates a
RaceWindow and connects its return signal back to the menu.

##### 2.35.1.1.2

MainMenuWindow (Player Setup)

Location:
Momentum/Python/GUI/gui_main_menu.py

This
is where players configure their race. The class loads the driver database via
DatabaseManager and presents a list of available drivers. Players select a
driver.

When
the player clicks Start Race the window emits a start_race_signal carrying a
config dictionary containing the selected driver and tuning preset.

##### 2.35.1.1.3

RaceWindow (Main Game View)

Location:
Momentum/Python/GUI/gui_race_visual.py

This
is the core gameplay class. It manages the visual track display, live car
rendering, standings table, and timing information. The RaceWindow contains
several key responsibilities:

* Track Generation: Uses
  CircuitGenerator to create a procedural racing circuit based on the track
  length. The circuit is built from straight sections and clothoid corner
  transitions and uses closure logic to complete a loop back to the start
  line.
* Race Execution: When the
  race starts the window spawns a race_runner thread that calls
  simulate_race from the race simulation API. This thread runs the
  RealtimeRaceEngine in the background and emits position updates at 30 FPS.
* Event Handling: The
  RaceWindow subscribes to position updates via EventEmitter signals. Every
  frame (30 times per second) the engine sends car positions, lap counts,
  gaps, and race status. The window updates the visual display and standings
  table based on these events.
* Player Input: The window
  captures input for pace adjustments and overtaking aggression. These
  inputs update player_overrides which the engine reads every tick to
  control the player's car.

##### 2.35.1.1.4

RealtimeRaceEngine (Simulation Core)

Location:
Momentum/Python/RaceLogic/realtime_race_engine.py

The
engine runs at 30 FPS and updates each driver's state every timestep (0.033s).
Each driver is represented by a DriverState object that tracks physical state
(position, velocity, lap), race situation (gaps, nearby cars), strategic state
(racing mode, push intensity), and component degradation (tires, fuel).

Main
loop steps per frame:

* AI Decision Making:
  update_racing_mode decides to attack, defend, manage pace, or cruise.
  Player-controlled drivers skip AI logic and use player_overrides.
* Performance Calculation:
  Speed based on driver attributes, team capability, push intensity, tire
  condition, fuel load, and slipstream.
* Position Update: Move
  car forward based on speed and timestep.
* Lap Detection: Detect
  crossing of start/finish, record lap times.
* Incident Checking:
  Detect collisions or incidents and log them.
* Degradation and Fatigue:
  Update tires, fuel, and push fatigue which affect mistake probability.
* Position Emission: Emit
  position events for the GUI to render.

##### 2.35.1.1.5

DatabaseManager (Persistence Layer)

Location:
Momentum/Python/database/database_manager.py

Handles
database operations for drivers, teams, tracks, championships, races, and race
results. Uses SQLite and initialises schema on first run. The engine queries
this manager to load driver and team data and, on race completion, results can
be persisted back to the database.

##### 2.35.1.1.6

VehicleRenderer (Visual Representation)

Location:
Momentum/Python/vehicles/vehicle_appearance.py

Renders
simplified top-down car sprites using PyQt's QPainter. Livery colors are
generated deterministically by team ID.

### 6.1.1

Objectives

Momentum aims to design and implement a prototype motorsport
management simulator that captures the scale, depth, and unpredictability of
real-world racing ecosystems. Unlike existing titles, which currently focus on
a limited range of disciplines (e.g., Formula 1 and limited feeder systems), it
will model a wide variety of racing disciplines, each with its own unique
challenges and culture. For example, rally racing will feature dynamic terrain
and weather, requiring teams to adapt strategies for gravel, tarmac, or snow.
Endurance racing will simulate human factors such as driver fatigue, teamwork,
and mechanical reliability over long events. Street racing will emphasise
customisation, driver personality, and the underground culture that shapes
rivalries and alliances. By capturing these distinctions, the simulator will
aim to represent a more varied and context-sensitive motorsport environment,
where each series presents different management challenges.

The objective is to simulate a persistent game world where
events unfold across all leagues, regardless of whether the player is directly
involved. By doing so, the system mirrors the emergent qualities of Football
Manager, supporting diverse career trajectories that may differ across
playthroughs.

A further objective is to offer a high degree of
customisation. Players will be able to modify or generate new teams, drivers,
and competitions. Procedural generation will be a cornerstone, enabling
large-scale fictional ecosystems that feel authentic while avoiding licensing
restrictions.

The project will demonstrate implementation across key areas
including simulation design and AI-driven decision-making. The intended
prototype will model core systems such as driver progression, economic
management, league standings, and race outcomes, with a focus on achieving
computational efficiency.

The project’s objective is to produce a management simulator
that can serve as a foundation for future extension. It seeks to address an
identified gap in current games by emphasising simulation depth and
customisation, rather than prioritising graphical fidelity.

### 6.1.2

Background

My passion for motorsport spans a wide range of disciplines,
from open-wheel racing to rally, endurance, and street racing. While some
recent games, such as The Crew Motorfest, successfully capture the unique feel
and culture of different racing series, they focus on driving experiences
rather than management. Existing management games, on the other hand, tend to
concentrate on a single discipline or lack the depth and variety needed to
authentically represent the full spectrum of motorsport. No current title
combines the breadth of racing types, the distinctiveness of each discipline,
and the emergent, persistent world of a management simulation. This project
seeks to address that gap by integrating the unique characteristics of multiple
racing series into a single, dynamic management experience.

Having spent extensive hours in Football Manager, I have
experienced the appeal of large, complex simulations that generate emergent
stories. Despite having a stronger interest in Formula 1 and motorsport
generally than in football, I find myself drawn more to Football Manager than
to existing motorsport management titles. This reveals an important insight:
the attraction lies not in the sport itself, but in the richness of the
simulated world.

By comparison, current motorsport titles such as F1 Manager
and Motorsport Manager are limited. Their focus is on presentation and visuals
rather than world depth. The lack of customisation and the narrow scope of
simulated leagues lead to repetitive experiences over time.

This project seeks to address this gap by exploring how the
thematic appeal of motorsport can be combined with the systemic depth
characteristic of Football Manager. The objectives outlined in Section 1.0 will
be met by designing algorithms that support persistent multi-league simulation,
driver development models, and financial/strategic systems. Procedural content
generation will be used to overcome licensing limitations and create a
fictional but believable motorsport ecosystem.

### 6.1.3

State of the Art

Current motorsport management titles include Motorsport
Manager (2016) and F1 Manager (2022–2024). These games present detailed races
and authentic visuals, but their simulation depth is fundamentally limited.
Driver development is linear and predetermined, making long-term play
predictable. Once a player has learned the optimal strategies, the outcomes
become repetitive. In contrast, Football Manager maintains replayability by
simulating an immense global ecosystem of leagues, players, and staff, where no
two careers are the same. This difference highlights the gap between motorsport
management games and the broader standard of emergent sports simulations.

Another limitation of existing motorsport titles is their
lack of customisation. Players cannot easily expand leagues, create fictional
scenarios, or reshape the competitive environment. The games are tightly
constrained by licensing agreements and static structures, which prevents the
freedom that makes Football Manager engaging. Furthermore, the game worlds are
small in scale, restricted to a handful of categories such as Formula 1 or
Formula 2, with little simulation occurring outside the top tiers. By comparison,
Football Manager tracks hundreds of leagues and thousands of clubs across
multiple nations, with events unfolding regardless of direct player
involvement.

This project aims to distinguish itself by adopting that
philosophy. The simulation will extend beyond open-wheel racing, with multiple
tiers within each discipline. Every league will progress whether the player
manages there or not, creating a sense of a living world. Because official
licensing is not available, all teams, drivers, and championships will be
procedurally created, which also allows experimentation with unique structures,
rivalries, and narratives. By prioritising breadth, depth, customisation, and
emergent systems, this project will investigate how principles seen in Football
Manager’s large-scale simulation might be adapted to a motorsport context.

It is worth noting that some recent non-management racing
games, such as The Crew Motorfest, have made significant strides in capturing
the unique feel, culture, and challenges of different racing disciplines. These
titles demonstrate that it is possible to authentically represent the diversity
of motorsport, from rally to endurance to street racing. However, they focus on
the driving experience and do not offer the persistent, emergent management
simulation that is central to this project. No current management title
integrates the breadth of racing types, the distinctiveness of each discipline,
and a persistent simulation world. This project aims to explore how these
elements can be combined within a prototype, developing a management simulator
that reflects both the variety and complexity of motorsport ecosystems.

### 6.1.4

Technical Approach

Momentum is being built using agile software principles. The
system is organised into three main parts: the Simulation Engine, Database
Management, and the Front-End Interface. Each part works together to create a
realistic and engaging motorsport management experience.

#### 6.1.4.1

Simulation Engine

The simulation engine is the heart of the system. Its design
is inspired by popular motorsport management games and research into
multi-agent systems. The engine handles things like how drivers improve over
time, how teams manage their finances, how races are decided, and how multiple
leagues can run at once. Race results are calculated using Monte Carlo
simulations, which take into account driver skills, car performance, track
details, weather, and random events. The financial side uses probability-based
models to reflect real-world unpredictability, such as changes in sponsorship
or unexpected costs. This means, for example, that a team with less money might
have to take more risks with their strategy, which can change how the whole
league plays out.

#### 6.1.4.2

Database Management

The database management system is responsible for creating
and storing all the teams, drivers, tracks, and championships. It uses
algorithms to generate these elements based on certain rules and probabilities,
ensuring that each league is balanced and diverse. Driver traits like skill,
temperament, and fatigue are set according to the needs of the league. Tracks
are created with different weather, locations, and surfaces, which all affect
how races play out. Team budgets and resources are also assigned by the
database, helping to create a dynamic and evolving competition. The system
keeps an eye on things like driver diversity and league balance, making
automatic adjustments to keep the game fair and interesting. All aspects of
content creation and generation are managed here, so references to procedural
generation are now part of database management.

#### 6.1.4.3

Front-End Interface

The front-end interface, built in Python, displays race
data, standings, driver stats, and financial dashboards. It shows the results
of simulations and AI decisions, and updates in real time as the game
progresses. When users make decisions or change strategies, these are sent to
the back end, which updates the league data. The interface provides instant
feedback on how the league is evolving and how the AI and database management
systems are affecting the game.

#### 6.1.4.4

Iteration, Feedback, and Scalability

The development plan is broken into clear phases, with
regular feedback and review. Progress is measured by tracking things like
driver development, AI improvements, financial stability, and the diversity of
the database-generated content. The system is designed to be modular, so new
features or motorsport types can be added without having to rebuild everything.
Data is stored efficiently to allow for long-term, multi-league play, making
Momentum a robust and replayable motorsport management simulator.

### 6.1.5

Technical Details

Momentum uses Python for both the front-end dashboards and
the back-end simulation logic and database management. The system relies on
NumPy for fast calculations, Pandas for handling data, and SciPy for advanced
statistics. The database uses SQLite to store all the information about
drivers, teams, tracks, and championships, making it easy to save and load
multi-season histories. All content creation and generation is handled by the
database management system.

#### 6.1.5.1

Race Outcome Simulation

Race results are produced by a real-time, agent based
engine. Each driver is modelled as an autonomous AI agent that makes decisions
on every simulation tick, targeting a frame rate of about 30 ticks per second.
Agents consider their attributes, car condition, tyre state, fuel, nearby
rivals, team orders and track conditions when choosing actions such as attack,
defend, overtake or conserve. Discipline specific rules are applied by the
engine to reflect differences between single seater, rally, endurance and other
formats. Randomness is retained for low probability events such as mechanical
failures or incidents so outcomes remain unpredictable, but most race behaviour
emerges from agent interactions rather than repeated sampling. Performance
sensitive results are cached where appropriate to keep leaderboards and UI
queries responsive.

#### 6.1.5.2

Driver Progression

Driver attributes like speed, consistency, aggression,
adaptability, and fatigue are tracked as numbers that can change over time. How
a driver develops depends on their past results, which are stored in the
database. Growth and decline are modelled using probability-based functions, so
each driver's career is unique. Fatigue and injuries are also tracked, with
recovery periods built in, making each season different and challenging.

#### 6.1.5.3

Data Management

All teams, drivers, tracks, and championships are created
and managed by the database management system. It uses algorithms to ensure
that everything is balanced and diverse, with different locations and themes
for tracks and championships. Before anything is saved, the system checks that
the league will be fair and interesting. This approach makes every playthrough
unique and replayable, and all content generation is now part of database
management.

#### 6.1.5.4

Performance Optimisation & Integration

The Python backend uses fast, vectorised calculations and
keeps frequently used data in memory for speed. League states are saved at the
end of each season, so progress is never lost. The system uses JSON to keep
everything in sync between the front end and database management. The design
makes it easy to add new features or motorsport types in the future, without
having to change the core of the game.

### 6.1.7

Project Plan

#### 6.1.7.1

Project Overview

Momentum will be developed in clear, manageable phases,
using agile methods. Each phase builds on the last, with milestones to track
progress. The plan ensures that the core systems are working before expanding
the database management system. Regular feedback and testing help refine the
algorithms and keep the simulation balanced and realistic.

#### 6.1.7.2

Requirements and Design

The first phase is about defining what the project will do,
how it will be structured, and how the database management system will work.
The main goals are to have realistic driver progression, dynamic race results,
and persistent multi-league play, with all teams, drivers, tracks, and
championships created and managed by the database system. The database will be
created before the game and packaged with it, so that every player has the same
starting point. Non-functional goals include making sure the system is
efficient, scalable, and easy to maintain. Design documents, diagrams, and
flowcharts will be created to clarify and organise the project plan. This phase
also sets performance targets and database designs and defines how the Python
components will communicate.

#### 6.1.7.3

Core Simulation Engine Development

The next phase is building the simulation engine, which is
the core of the project. This includes setting up league structures, how
drivers improve, how finances work, and how races are decided. Driver skills,
fatigue, and personality are modelled using probability-based systems. Team
finances, including budgets and sponsorships, are also handled with realistic
randomness. Race results are calculated using Monte Carlo simulations,
considering all the important factors. Data is managed efficiently to keep the
game running smoothly, even with many leagues and seasons.

#### 6.1.7.4

Database Management

Once the simulation engine is working, the focus shifts to
the database management system. This part is responsible for creating and
storing all teams, drivers, tracks, and championship schedules. It uses
algorithms to make sure everything is diverse and balanced, with different
locations and themes. Before anything is saved, the system checks that the
league will be fair and interesting. This phase also adds tools for batch
creation and automatic checking of content, making sure every playthrough is unique
and replayable.

#### 6.1.7.5

Front-End Integration

The Python front end is connected to the backend to show
race data, leaderboards, team dashboards, and driver stats. Updates are sent
smoothly to keep the interface responsive. The user interface is tested for
clarity and ease of use. Integration ensures that all changes from the
simulation and database management systems are shown accurately in the game.

#### 6.1.7.6

Iterative Testing and Refinement

Testing happens in cycles, with milestones for things like
driver development, financial stability, AI variety, realistic race results,
and multi-league play. Feedback from each cycle is used to improve the
algorithms and keep the simulation balanced. The system is monitored to make
sure rivalries, race outcomes, and league progression all feel realistic.
Performance is checked and improved as needed to keep everything running
smoothly.

#### 6.1.7.7

Final Evaluation and Documentation

The final phase reviews how the system behaves, the user
experience, stability, and overall performance. All code is documented, and
detailed reports are created on simulation accuracy and database management.
This phase makes sure that Momentum works as a complete, persistent, and
scalable motorsport management simulator, meeting all the goals set out at the
start.

The project plan is designed to move smoothly from design to
deployment, with clear milestones and dependencies. Regular feedback and
testing ensure that Momentum delivers a realistic and engaging experience,
while staying easy to maintain and expand in the future.

### 6.1.8

Testing

#### 6.1.8.1

Testing Strategy

Testing for Momentum is structured across multiple levels to
ensure system stability, performance, and fidelity of simulation outcomes.
Unit, integration, system, and user testing are all incorporated to validate
both functional and non-functional requirements. Each level of testing is
designed to produce measurable results and inform iterative refinement cycles
throughout development. Ethical considerations, including data privacy,
informed consent, and participant anonymity, are integrated into all user evaluation
procedures.

#### 6.1.8.2

Unit Testing

Unit testing validates individual modules of the simulation.
Driver progression, financial systems, race outcome calculations, and AI
decision-making routines are tested against expected behaviours and edge cases.
Probabilistic models for driver skill development, fatigue, and personality
traits are verified for correct statistical distribution and consistency.
Financial operations are checked for accuracy, ensuring budgets, sponsorships,
and costs are correctly computed under stochastic conditions. Race outcome
algorithms, including Monte Carlo simulations, are validated to maintain
realistic variability while ensuring balance between drivers and teams.

#### 6.1.8.3

Integration Testing

Integration testing ensures proper communication between the
Python back-end,  front-end, AI modules,
and procedural content generation systems. JSON-based data exchanges are
verified for accuracy and latency, and SQLite storage operations are tested for
integrity across multi-season and multi-league scenarios. Metrics include data
consistency, transaction success rates, and persistence reliability.
Integration tests also verify that AI decisions, procedural generation outputs,
and race telemetry are correctly reflected in the user interface, maintaining
coherent emergent behaviours across the simulation.

#### 6.1.8.4

System Testing

System-level testing evaluates Momentum under full
operational conditions. Multi-league, multi-season simulations are run to
assess emergent behaviour, computational performance, and scalability. Metrics
include league variability, AI decision diversity, race outcome distribution,
system load, and memory usage. Stress testing is performed to evaluate
performance under high concurrency and extended simulation periods. Any
bottlenecks in AI computation, procedural content generation, or database
operations are identified and addressed to maintain real-time responsiveness
and persistent state accuracy.

#### 6.1.8.5

User Evaluation

User testing measures interface usability, engagement, and
comprehension of the management systems. Participants interact with the
full  front-end, reviewing dashboards,
race summaries, and team management tools. Quantitative metrics include task
completion time, accuracy of actions, and interaction frequency. Qualitative
metrics are gathered via structured surveys, focusing on perceived realism,
clarity, and enjoyment. Ethical safeguards are enforced, including informed
consent, voluntary participation, and secure handling of collected data.
Feedback informs both interface improvements and algorithmic refinements to
maintain realistic, emergent gameplay.

Overall, the testing framework ensures that Momentum
achieves persistent, scalable, and believable motorsport simulation. Iterative
results from unit, integration, system, and user testing directly guide
algorithm adjustments, AI behaviour tuning, procedural content balancing, and
front-end enhancements, guaranteeing a coherent, high-quality, and engaging
management experience.
